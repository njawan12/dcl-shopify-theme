## 2. Exact visual hypothesis

Evidence Rail is a recognizable subject → attached numbered evidence → visible qualification/source rhythm embedded in PDP media/education and editorial storytelling. A continuous logical edge connects evidence encounters; large evidence values, paired subjects and numbered process steps participate in the rail rather than sitting in a conventional icon grid with decorative numbers. The subject and commerce hierarchy remain clear. Desktop may use bounded asymmetric tracks; mobile compresses the same rail to a linear, readable sequence from the same DOM. Shared M1 scale contrast, negative space, edge relationships and tokens; no copied Split Tension/Mosaic composition or new design system.

Rail numbers identify evidence encounters, not review ratings, efficacy ranks or a process order unless the primitive is an ordered process. No icons, stars, fake seals, counters, motion dependency or bespoke photography rescue. A rail does not imply source credibility.

## 3. Smallest coherent semantic system

Three narrow renderers, not a universal section or one component per evidence kind:

- **Evidence Note:** metric, ingredient/material/specification/nutrition fact, claim, certification, merchant-authored testimonial/editorial quote. PDP-media and editorial attachments. Distinct kind labels make factual content, attributed claims and authored quotation distinguishable.
- **Evidence Pair:** before/after or comparison, separate semantic modes sharing paired-context rendering in PDP education. Before/after is static; no slider. Comparison uses explicit named subjects and complete rows, no inferred winner.
- **Process Sequence:** usage/care/process, ordered instructions in PDP education or editorial. One valid surviving step stays an ordered one-step process.

PDP media notes, PDP education pair/process and editorial note OR process are separate narrow attachments. No purchase form is reordered or rewritten. Read-only product links/context suffice for isolated host proof, not full PDP commerce.

## 4. Truth and content schemas

All fixtures are visibly labelled synthetic test content, not real clinical evidence, endorsements or verified reviews. Standard manually authored fields create a complete polished result. Optional dynamic-source-shaped bindings populate the identical schema; no proprietary evidence store, network, validation service or mandatory metafields. Explicit connected values or manual fallback only; disconnected values never silently persist.

Note has eight fields: kind, value, label, body, attribution, source_title, source_url, qualification. Metric requires value+label; units/scope belong to label/body/qualification, source optional. Fact requires label and value or body. Claim requires body; qualification states material limits. Certification requires label/name+issuer attribution and scope in body/qualification. Quote requires body+attribution and displays “Merchant-authored quotation”; never verified-buyer status, rating or review count. Theme renders supplied content, never assesses source credibility, factual trustworthiness or merchant claim validity.

Pair shared fields: heading, introduction, qualification, source_title, source_url, semantic mode. Before/after exactly two labelled media records (label, media, alt, caption), genuine related content required in production; synthetic schematic pairs must say so. Explicit alternatives and labels survive without media. Incomplete pair is omitted, not recast as a valid result. Comparison exactly two named subjects, maximum four rows: criterion, left, right, qualification. Remove incomplete rows; omit pair without subjects/complete rows. No competitor/discount math.

Process shared fields: heading, introduction, source_title, source_url. Maximum four steps: heading, instruction, media, alt, qualification. Required heading+instruction; remove invalid steps and renumber consecutively. One step remains `<ol><li>`. Media optional; usage cannot silently become an efficacy claim.

Omit empty optional fields without residual punctuation/spacing. Omit invalid note. Invalid/missing optional media disappears, valid text remains. Source title remains text when URL absent/invalid. Links only for structurally valid HTTP(S), supported root-relative paths or resolvable same-document fragments, with contextual escaping. No “unsafe source”, credibility, claim validity or remote availability assessment. Unsupported schemes/malformed URL/unresolved fragment get no link. Zero evidence leaves a coherent subject/commerce host; no shopper-facing editor errors.

## 6. Order, responsive semantics and accessibility

PDP: subject title/media → read-only truthful product context/destination → media-attached notes → distinct pair/process education sections in merchant order. Editorial: statement/media → notes OR process → editorial destination. Each note: kind/encounter identifier, value/statement, qualification/attribution/source. Pair: heading/context → before then after, or criterion with left then right values → shared qualification/source. Process: heading/context → ordered steps → source. Apps appear at their host block encounter, outside evidence lists and media masks; normal-flow guest breaks/resumes rail visually without joining its numbered claim sequence.

One DOM at every width, no CSS `order`, no masonry or duplicated responsive content. At 320–430 preserve subject recognition, readable qualifications and full native targets; tablet relaxes asymmetry before collision; desktop bounded tracks. Logical properties support RTL feasibility, not RTL certification. No fixed text heights, hidden qualifications, text clipping, hover-only meaning or color-only truth. Native headings, lists, blockquotes/figcaptions, table headers/captions; meaningful alt; source/destination links; skip link and visible focus; 44px internal interactive targets. Reflow and 50% translation expansion/unbroken strings must work. Zero runtime JS and no motion: delayed/failed JS and reduced motion cannot erase evidence.

## 7. App architecture and evidence boundary

Official architecture revalidated 2026-10-05: [Shopify app blocks](https://shopify.dev/docs/storefronts/themes/architecture/blocks/app-blocks). JSON-template section schema accepts generic `{ "type": "@app" }` without `limit`; section-defined blocks dispatch `@app` via `{% render block %}`. Theme-block contexts use `content_for 'blocks'`; this specimen intentionally chooses section-defined block dispatch, not both. No vendor API or dependency. Do not target vendor internals or bake a review widget into theme output.

Include a non-deployed Liquid seam specimen under the isolated prototype, not production directories. Test schema/dispatch plus independently authored guest fragments (plain test document, tall text, wide fixed-width table) at expected and awkward host encounters, absent/removed/reordered/duplicated. No guest ratings/reviews. Host permits intrinsic growth; an accessible labelled overflow region confines genuinely wide guest content without clipping it. Do not promise every malformed external widget is automatically accessible. Live Shopify Liquid/app/editor execution is a separately reported untested gate; static specimen and local geometry must never be represented as live integration certification.
