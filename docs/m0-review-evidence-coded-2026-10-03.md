# M0 coded review evidence — 2026-10-03

## Scope and evidence rule

This is a dated qualitative coding pass of current/recent official Shopify Theme Store reviews across the eight-theme competitor sample. It is intended to test problem signals, counter-evidence, and support burden. It does not infer sales, market share, or population prevalence from review anecdotes.

## Coding taxonomy

- OPERABILITY_POSITIVE — intuitive/easy to use or customize
- OPERABILITY_FRICTION — difficult navigation/configuration or non-technical user friction
- CUSTOM_CODE — desired outcome required or benefited from code/custom development
- SUPPORT_DEPENDENCE — support materially enabled setup, repair, integration, or modification
- UPDATE_REGRESSION — update introduced/raised concern about breakage
- APP_INTEGRATION — third-party app/integration issue
- FEATURE_GAP — merchant expected a missing/bounded capability
- MOBILE_LAYOUT — mobile/cropping/layout concern
- INTERNATIONALIZATION — language/currency/localization concern
- PERFORMANCE — merchant-reported performance concern
- COUNTER_EVIDENCE — evidence that incumbent already solves part of DCL's proposed problem well

## What the coded evidence says

### 1. Support is not peripheral

Across every sampled theme, current/recent reviews repeatedly make support part of the value proposition. Support handles configuration questions, custom-code requests, upgrades, third-party-app diagnosis, and fixes. This means DCL must model support as a real cost center rather than assume a one-time theme sale is mostly passive revenue.

### 2. The strongest opportunity is not generic no-code

There is substantial counter-evidence. Broadcast, Symmetry, Motion, Impact and others receive explicit praise for ease, flexibility and self-management. A DCL theme that merely advertises “easy to customize without code” would enter occupied territory.

### 3. Complexity displacement remains worth testing

The same themes can be praised for breadth while other merchants report difficulty navigating features, missing expected controls, needing custom work, or wanting preloaded/demo starting states. The sharper hypothesis is not that incumbents are unusable; it is that **feature breadth creates avoidable decision/support cost for recurring commercial jobs**.

### 4. Starting-state quality may be commercially important

The Impact review requesting demo/sample content after seeing an empty theme is a direct problem signal. Broadcast merchants praise its easy templates, which is counter-evidence. M1 therefore needs to compare job-oriented starts against a credible incumbent-style template/preset baseline—not against an artificially empty canvas.

### 5. Updates and ecosystem interactions must be product requirements

Reviews show update regressions and app issues even in highly mature themes. Architecture must minimize fragile customization surfaces, preserve predictable upgrade behavior where possible, and define app ownership boundaries clearly.

## Decision impact

The M0/M1 research design should be tightened in one important way:

**B0 must not be a straw-man blank canvas.** The baseline should represent a strong contemporary premium-theme workflow: a relevant preset/template plus its existing configurable sections. DCL's B1 job-oriented composition must beat that credible baseline on time, consequential decisions, recovery, and output coherence.

If B1 only beats an empty generic page, the differentiation claim is not credible.

## Remaining evidence gap

This coded set is intentionally qualitative. The repository gate still requires at least 50 recent reviews in the formal evidence workbook/sample and controlled competitor task teardowns. Additional observations should be sampled systematically rather than selected only for friction, including positive/counter-evidence reviews.
